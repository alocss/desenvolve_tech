The new sections reused the right building blocks — but reused the same one six times over. Every section entering with an identical spring-blur, and two lists staggering in the same view, is the classic AI-generated tell. Both are fixed: static text now renders instantly, and only one section per page gets to stagger.

Where the timings land

This is a low-frequency marketing page, not a productivity tool — a visitor triggers each reveal once per visit, scrolling past it, not dozens of times a session. Durations plotted where they run today.

The animations

  2. 2Card border/icon hover250ms
  3. 3.hero-enter (mount, CSS-only)400ms
  4. 4RevealItem spring (grid cards)~500ms
  5. 5Reveal spring (single blocks)~550ms
Instant / Responsive · 0–300ms — hover and press feedback lands here, correctly.
Deliberate · 300–500ms — earned by page-load and viewport-triggered content moments.
Sluggish · 500ms+ — flags a repeated interaction; not what's happening here.
What's off

Nothing needs a fix here. Dot 5 (~550ms) technically crosses into Emil's generic "sluggish" line, but that line is calibrated for repeated interactions — this is a once-per-visit, scroll-triggered content reveal on a marketing page, which is exactly the context where Jakub and Jhey's longer, more deliberate pacing is the right call. Flagged for transparency, not for action.

Issues to address
ImportantJakubFixed in this pass

Six sections shared one identical enter animation — including plain text

WhatThe new home page wrapped six distinct blocks — the institutional intro paragraph, the services grid, the portfolio teaser panel, the differentiators grid, and the closing CTA panel — in the exact same Reveal/RevealGroup spring (opacity + 12px translateY + 4px blur, ~500–550ms). Two of those six were plain headings and paragraphs with no card, image, or grid to justify a "moment."

Why it mattersUniform treatment across ≥4 distinct components is the anti-checklist's own uniformity threshold — it's the fingerprint of an AI-generated page, not a designed one. And motion on text-only content delays reading for no functional reason; it announces the entrance instead of getting out of the way.

Recommended motionReserve the reveal for actual card-grid moments (services, differentiators, the portfolio panel). Plain text and CTA panels render instantly — matching the site's own existing precedent on /servicos, whose closing CTA already ships with zero scroll motion.

Issues to address
ImportantJheyFixed in this pass

Two card grids staggered in the same view

WhatThe new "O que nos diferencia" grid used RevealGroup/RevealItem with staggerChildren — the same treatment already used by the "O que fazemos" services grid just above it. Both would stagger in the same page.

Why it mattersStagger works because it reads as a moment — a deliberate, singular cascade. Two staggered grids on one page dilute that; the second stagger doesn't feel special, it feels like the same trick fired twice.

Recommended motionKeep staggerChildren reserved for Services — the page's first and primary content grid. The differentiators grid (and the future portfolio-cases grid, same page) now fade in as one block via a single Reveal, no per-card stagger.
